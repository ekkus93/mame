# MT-1404 through MT-1407 — CI maturation

**Document date:** 2026-09-13

This document defines the native/Tauri validation routing, representative MAME build strategy, cross-platform execution matrix, and exact-head release evidence process.

## MT-1404 — Representative native MAME validation

`SUBTARGET=tiny` is the fast representative native MAME target.

- Linux already builds and executes `mametiny -validate` on the GCC matrix leg and preserves a full `mame -validate` Clang leg.
- Windows ordinary native changes now build `SUBTARGET=tiny`, `TOOLS=0`, and execute `mametiny.exe -validate` on `windows-latest`/CLANG64.
- macOS ordinary native changes now build `SUBTARGET=tiny`, `TOOLS=0`, and execute `mametiny -validate` on `macOS-latest`.
- The pre-existing expensive Windows three-leg/full-tool matrix and full macOS MAME build remain available for tags and `workflow_dispatch`.

This gives native changes an executable cross-platform signal without forcing every branch update through every release-sized MAME build.

## MT-1405 — Path-based routing

Native MAME workflows watch project/core inputs such as `src/**`, `3rdparty/**`, `hash/**`, root build files, and their own workflow file.

`tauri/**` does not trigger those native MAME workflows. `scripts/**` is included for native tooling, with `scripts/tauri/**` explicitly excluded. Tauri/frontend changes are instead handled by the Tauri project and packaging workflows.

Changing a native CI workflow file triggers that workflow's representative validation. This makes CI-routing changes self-testing.

## MT-1406 — Cross-platform matrix

| Platform | Ordinary native branch/PR | Release/manual native validation | Tauri/package validation | Compile-only or executable? |
| --- | --- | --- | --- | --- |
| Linux | GCC `tiny` plus Clang full `mame` | Same native matrix; package workflow separately validates `.deb`/AppImage | Tauri quality, X11 application smoke, `.deb` install/uninstall, AppImage launch/extraction | Executable: `-validate` and package/app smoke |
| Windows | CLANG64 `tiny` | GCC x64 full MAME, Clang x64 `tiny`, Clang ARM64 full MAME | NSIS build plus clean install/resource/uninstall smoke | Executable: `mametiny.exe -validate` / `mame.exe -validate` and installer smoke |
| macOS | `tiny` | full MAME | app/DMG build, relocation/resource/signature smoke | Executable: `mametiny -validate` / `mame -validate` and package smoke |

No listed native matrix leg is compile-only: each representative/full native build runs its generated MAME executable with `-validate`. Package workflows likewise exercise built/installed artifacts rather than treating successful compilation as sufficient.

## MT-1407 — Exact-head evidence

Use the repository-owned helper:

```sh
python3 scripts/tauri/report-ci-evidence.py --sha <40-character-candidate-sha>
```

The default release set is:

- `Tauri project`
- `Tauri Linux packaging`
- `Tauri Windows packaging`
- `Tauri macOS packaging`

The helper queries workflow runs for the exact requested SHA, chooses the newest exact-SHA run for each required workflow, and returns success only when every required workflow is present, completed, and concluded `success`.

JSON output for release tooling is available with:

```sh
python3 scripts/tauri/report-ci-evidence.py --sha <sha> --json
```

Additional gates can be required explicitly, for example:

```sh
python3 scripts/tauri/report-ci-evidence.py \
  --sha <sha> \
  --require 'Tauri project' \
  --require 'Tauri Linux packaging' \
  --require 'Tauri Windows packaging' \
  --require 'Tauri macOS packaging' \
  --require 'Build documentation'
```

The helper itself has offline regression coverage in `scripts/tauri/test-report-ci-evidence.py`, which is executed by `Tauri project` CI.

## Release evidence checklist

Before declaring a release/closure candidate qualified:

1. Freeze the exact 40-character candidate SHA.
2. Run `report-ci-evidence.py` against that SHA; do not substitute branch-head or “latest run” evidence.
3. Record the candidate SHA and workflow run IDs in the release/closure document.
4. Require additional native/upstream gates when the candidate changes native MAME code.
5. If any closure documentation changes the SHA, distinguish the executable implementation SHA from the docs-only closure SHA and qualify the latter with the documentation workflow.
6. Do not treat a green run for an ancestor, descendant, or different branch head as qualification evidence for the candidate.
